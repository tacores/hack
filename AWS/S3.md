## 基本

### Access Control Lists (ACLs)

S3 バケットアクセス制御の従来の方法。2021 年以降、ACL を無効にするよう推奨されている。

### Bucket Policy

ACL と似ているが、Human-Readable な形式で、推奨されている。「リソースベースポリシー」と呼ばれるようになった最初の例。AWS における ID ベースの権限は IAM プリンシパルに紐付けられているのに対し、リソースベースポリシーは接続されたリソースへの直接アクセスを許可する。つまり、ポリシーでグローバルな読み取りおよび書き込みアクセスが許可されている場合、バケット内のデータを表示したり、バケットに新しいファイルを追加したりするために AWS 認証情報は必要ない。

| **Layer**               | **制御する内容**                                 | **Overridden by**   |
| ----------------------- | ------------------------------------------ | ------------------- |
| **Access Control List** | バケットやオブジェクトを一覧表示・読み取りできるユーザー               | Block Public Access |
| **Bucket Policy**       | アクション単位・プリンシパル単位で細かくアクセスを制御するルール           | Block Public Access |
| **Block Public Access** | アカウントレベルまたはバケットレベルで、すべてのパブリックアクセスをブロックする設定 | None                |

## CloudFront "Origin"

CloudFront の背後でホストされているリソースのこと。オリジンアクセスアイデンティティ（OAI）とは、特定の CloudFront リソースのみが CloudFront オリジンの背後にある S3 バケットにアクセスできるようにすることを意味する。

OAI 設定例

```json
{
  "Sid": "1",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::cloudfront:user/CloudFront Origin Access Identity EAF5XXXXXXXXX"
  },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::{your_bucket}/*"
}
```

特定したコンテンツのホストが CloudFront だとわかれば、ホストされているリソースを特定することができる。OAI が適切に設定されていない場合、オリジンに直接アクセスすることができ、CloudFront で実装されているセキュリティ制御がバイパスされてしまう。

### Object Ownership

ACLを使うかどうか、誰がオブジェクトを所有するか

```sh
$ aws s3api get-bucket-ownership-controls --bucket $BUCKET_NAME

{
    "OwnershipControls": {
        "Rules": [
            {
                "ObjectOwnership": "BucketOwnerPreferred"
            }
        ]
    }
}
```

このバケットに対してACLが有効であることを意味する。

### Public Access Block

#### bucketレベル

```sh
aws s3api get-public-access-block --bucket $BUCKET_NAME

{
    "PublicAccessBlockConfiguration": {
        "BlockPublicAcls": false,
        "IgnorePublicAcls": false,
        "BlockPublicPolicy": false,
        "RestrictPublicBuckets": false
    }
}
```

falseは設定されていないことを意味する。

#### アカウントレベル

```sh
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
aws s3control get-public-access-block --account-id $ACCOUNT_ID

{
    "PublicAccessBlockConfiguration": {
        "BlockPublicAcls": false,
        "IgnorePublicAcls": false,
        "BlockPublicPolicy": false,
        "RestrictPublicBuckets": false
    }
}
```

## 暗号化

https://tryhackme.com/room/theplainbucket

SSEは Server-Side-Encryption

| **タイプ** | **SSE-S3** | **SSE-KMS** | **SSE-C** |
|---|---|---|---|
| **キー管理元** | AWS（S3マネージドサービス） | AWS（KMSマネージド） | 顧客（外部） |
| **デフォルトオプション** | はい（自動） | いいえ（有効にする必要があります） | いいえ |
| **監査証跡** | いいえ（基本ログのみ） | はい（CloudTrail経由） | いいえ |
| **料金** | 無料 | KMSキー＋リクエスト料金 | 無料 |
| **鍵の回転** | S3によって管理されています | 顧客/AWS管理 | 顧客管理 |
| **アクセス制御** | 標準IAM/バケットポリシー | IAM/KMSキーポリシー | クライアントヘッダー経由で管理 |
| **最適な用途** | 一般的な用途 | セキュリティとコンプライアンスの強化 | 法的要件／レガシー要件 |

- SSE-S3は、S3の読み取り権限があれば、取得時にオブジェクトを自動的に復号化する。つまり、S3のインフラ自体が侵害された状況を想定した暗号化と考えられる。
- SSE-KMSを使用する場合、オブジェクトを復号化するために kms:Decrypt 権限が必要

バケットレベルの暗号化設定を確認

```sh
aws s3api get-bucket-encryption --bucket "$BUCKET_NAME"
```

オブジェクトの暗号化設定

```sh
aws s3api head-object --bucket "$BUCKET_NAME" --key sample-data.txt \
    --query '{SSE:ServerSideEncryption,SSEKMSKeyId:SSEKMSKeyId}'
```

## S3サーバーアクセスログと CloudTrail S3データイベント

https://tryhackme.com/room/theblindbucket

サーバーアクセスログはリクエストごとの詳細な記録を提供し、CloudTrailのデータイベントはセキュリティ監視のためのIAMコンテキストと統合を提供する。両方を有効にしておくのが良い。

| **項目**          | **S3サーバーアクセスログ**           | **CloudTrail S3データイベント**                             |
| --------------- | -------------------------- | ---------------------------------------------------- |
| **記録対象**        | バケットへのすべてのHTTPリクエスト        | APIレベルのデータ操作（例：`GetObject`、`PutObject`）              |
| **配信遅延**        | 数分～数時間                     | 約15分                                                 |
| **形式**          | スペース区切りのログ行                | JSON                                                 |
| **IAMアイデンティティ** | 含まれない（IPアドレスやUser-Agentのみ） | 含まれる（呼び出し元の完全なARN）                                   |
| **連携先**         | S3プレフィックス検索                | CloudWatch Logs、CloudWatch Insights、Athena、GuardDuty |

- S3データイベントはデフォルトでは無効になっている。各バケットに対して、データイベントセレクタを明示的に追加する必要がある。これを行わないと、GetObject および PutObject 操作は CloudTrail で全く表示されない。
- S3サーバーアクセスログはCloudTrailデータイベントを補完する。
